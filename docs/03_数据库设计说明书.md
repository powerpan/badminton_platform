# 数据库设计说明书

## 1. 设计目标

数据库用于保存 BF羽毛球馆管理平台的核心业务数据，包括用户、会员账户、场地、预约、预约订单、公告、站内通知、活动赛事、球友圈、商城、系统配置和操作日志。设计目标是保证数据结构清晰、业务状态可追踪，并能支持普通用户预约、预约余额支付、会员余额扣款、活动报名、动态发布、商城余额支付和管理员后台管理。

## 2. 命名规范

- 表名使用小写英文和下划线。
- 主键统一使用 `id`。
- 创建时间统一使用 `created_at`。
- 更新时间统一使用 `updated_at`。
- 状态字段统一使用 `status`。
- 删除操作优先使用状态控制，避免直接物理删除关键业务数据。

## 3. 核心实体关系

```text
user 1 --- 1 member_account
user 1 --- n reservation n --- 1 court
reservation 1 --- 0..1 reservation_order
member_account 1 --- n member_account_transaction
reservation 1 --- n member_account_transaction
user 1 --- n event_registration n --- 1 club_event
user 1 --- n community_post
user 1 --- n shop_order 1 --- n shop_order_item n --- 1 shop_product
shop_order 1 --- n member_account_transaction

announcement 独立保存公告信息
notification 记录用户站内通知和已读状态
config       独立保存系统规则
operation_log 记录用户和管理员关键操作
```

### 4.2 会员账户表 member_account

用途：保存用户会员等级、余额、积分和有效期。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| user_id | bigint | primary key | 用户ID，同时关联 `user.id` |

| updated_at | datetime | not null | 更新时间 |

说明：

- 固定等级折扣为：普通会员 100%，银卡 95%，金卡 90%，钻石 85%。
- 预约日期晚于 `expires_at` 时，折扣按普通会员计算。
- 余额只能通过后台调整或预约退款增加，用户端不做自助充值。

### 4.4 预约表 reservation

用途：保存用户预约记录。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | bigint | primary key, auto increment | 预约ID |
| reservation_no | varchar(64) | not null, unique | 预约编号 |
| user_id | bigint | not null | 用户ID |
| court_id | bigint | not null | 场地ID |
| reserve_date | date | not null | 预约日期 |
| start_time | time | not null | 开始时间 |
| end_time | time | not null | 结束时间 |
| time_slot | varchar(50) | not null | 展示用时间段，例如 09:00-10:00 |
| status | varchar(20) | not null | 状态 |
| remark | varchar(255) | null | 备注 |
| price_per_hour_cents | int | not null, default 12000 | 创建预约时的场地小时价格快照，单位分 |
| duration_minutes | int | not null, default 60 | 预约时长，单位分钟 |
| original_amount_cents | int | not null, default 12000 | 原始金额，单位分 |
| discount_amount_cents | int | not null, default 0 | 优惠金额，单位分 |
| payable_amount_cents | int | not null, default 12000 | 应付金额，单位分 |
| member_level_snapshot | varchar(20) | not null, default normal | 创建预约时实际使用的会员等级 |
| discount_rate | int | not null, default 100 | 创建预约时实际使用的折扣率 |
| points_awarded | int | not null, default 0 | 本次预约发放积分 |
| created_at | datetime | not null | 创建时间 |
| updated_at | datetime | not null | 更新时间 |
| canceled_at | datetime | null | 取消时间 |

建议索引：

- `uk_reservation_no(reservation_no)`
- `idx_reservation_user(user_id)`
- `idx_reservation_court_date(court_id, reserve_date)`
- `idx_reservation_status(status)`
- `idx_reservation_slot(court_id, reserve_date, start_time, end_time)`

预约状态建议：

| 状态 | 说明 |
| --- | --- |
| pending | 待支付，表示时间段被临时占用 |
| confirmed | 已确认，表示预约订单已支付，时间段被正式占用 |
| canceled | 已取消 |
| expired | 超时释放 |
| completed | 已完成 |

说明：

- 当前版本创建预约时先写入 `pending`，同时生成 `reservation_order` 待支付订单。
- 待支付订单支付成功后，系统在同一个 MySQL 事务内扣减会员余额、写入会员流水、将订单改为 `paid`，并将预约改为 `confirmed`。
- 待支付订单超时后会改为 `expired`，场地占用随之释放。
- 金额、会员等级、折扣率和积分字段都是预约创建时的快照。后续修改场地价格或会员等级不会覆盖历史预约金额。
- 有效预约状态通常包括 `pending` 和 `confirmed`，冲突校验时需要排除 `canceled`、`expired`。

### 4.4.1 预约订单表 reservation_order

用途：保存预约待支付订单和余额支付状态。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | bigint | primary key, auto increment | 预约订单ID |
| order_no | varchar(64) | not null, unique | 预约订单号 |
| reservation_id | bigint | not null, unique | 关联预约ID |
| user_id | bigint | not null | 下单用户ID |
| status | varchar(20) | not null, default pending | 状态，pending/paid/canceled/expired |
| amount_cents | int | not null, default 0 | 支付金额，单位分 |
| pay_method | varchar(20) | not null, default balance | 支付方式，当前为会员余额 |
| expires_at | datetime | not null | 待支付截止时间 |
| paid_at | datetime | null | 支付时间 |
| canceled_at | datetime | null | 取消时间 |
| cancel_reason | varchar(255) | null | 取消原因 |
| created_at | datetime | not null | 创建时间 |
| updated_at | datetime | not null | 更新时间 |

建议索引：

- `uk_reservation_order_no(order_no)`
- `uk_reservation_order_reservation(reservation_id)`
- `idx_reservation_order_user(user_id)`
- `idx_reservation_order_status(status)`
- `idx_reservation_order_expires(status, expires_at)`

并发与原子性说明：

- 创建预约订单只写入 `pending` 预约和 `pending` 订单，不扣会员余额。
- 余额支付时使用事务锁定 `reservation_order`、`reservation` 和 `member_account` 行。
- 只有订单和预约都仍为待支付且未过期时才扣款；扣款、发积分、订单 `paid` 和预约 `confirmed` 同事务提交。
- 重复支付或并发支付只能有一个事务成功，后续请求会看到订单已不是 `pending`，不会重复扣款。

### 4.5 会员账户流水表 member_account_transaction

用途：记录余额和积分变化，便于追踪预约扣款、取消退款和后台调整。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | bigint | primary key, auto increment | 流水ID |
| user_id | bigint | not null | 用户ID |
| reservation_id | bigint | null | 关联预约ID，后台调整和商城订单时为空 |
| shop_order_id | bigint | null | 关联商城订单ID，非商城流水时为空 |
| transaction_type | varchar(50) | not null | 流水类型，admin_adjust/reservation_charge/reservation_refund/shop_purchase/shop_refund |
| balance_change_cents | int | not null, default 0 | 余额变动，单位分，可正可负 |
| points_change | int | not null, default 0 | 积分变动，可正可负 |
| balance_before_cents | int | not null | 变动前余额 |
| balance_after_cents | int | not null | 变动后余额 |
| points_before | int | not null | 变动前积分 |
| points_after | int | not null | 变动后积分 |
| reason | varchar(255) | null | 变动原因 |
| operator_id | bigint | null | 操作人ID |
| operator_username | varchar(50) | null | 操作人用户名 |
| created_at | datetime | not null | 创建时间 |

说明：

- 预约成功会写入 `reservation_charge`，余额扣减，应付金额按 1 元 1 分发放积分。
- 取消预约会写入 `reservation_refund`，退回本次应付金额，并扣回本次发放积分。
- 商城余额支付写入 `shop_purchase`，取消退款写入 `shop_refund`。
- 后台会员调整写入 `admin_adjust`，并同步写入操作日志。

## 5. 建表 SQL 草案

以下 SQL 可作为后续开发的初始版本，实际实现时可根据 ORM 或迁移工具调整。

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  nickname VARCHAR(50) NULL,
  role VARCHAR(20) NOT NULL DEFAULT 'user',
  contact VARCHAR(50) NULL,
  status TINYINT NOT NULL DEFAULT 1,
  last_login_at DATETIME NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_user_username (username),
  KEY idx_user_role (role),
  KEY idx_user_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE member_account (
```

## 6. 预约冲突判断

预约冲突判断需要同时考虑 Redis 和 MySQL：

1. Redis 先加锁，锁 key 建议为 `reservation:lock:{court_id}:{reserve_date}:{start_time}:{end_time}`。
2. 加锁成功后进入 MySQL 短事务。
3. 事务内锁定当前用户行、会员账户行和场地行，重新确认用户、场地状态，并读取场地价格和会员余额。
4. 事务内查询该用户当天有效预约，用于校验每日预约次数。
5. 事务内查询同一场地、同一日期、`pending/confirmed` 状态的重叠预约。
6. 时间重叠条件为：`new_start < old_end AND new_end > old_start`。
7. 如果 MySQL 无冲突且会员余额足够，则在同一事务内写入预约记录、费用快照、扣减余额、发放积分并提交。
8. 如果发生冲突或写入失败，需要回滚事务并释放 Redis 锁。
9. 如果预约取消或超时，需要更新 MySQL 状态，并释放或等待 Redis key 过期。

说明：Redis 锁用于降低同一时间段的并发冲突概率，MySQL 事务是最终一致性保护。这样可以覆盖“09:00-11:00”和“10:00-12:00”这类起止时间不同但实际重叠的预约请求。

费用快照计算规则：

- `duration_minutes = end_time - start_time`
- `original_amount_cents = price_per_hour_cents * duration_minutes / 60`
- `discount_rate` 按预约日期对应的有效会员等级计算，普通/银卡/金卡/钻石分别为 100/95/90/85
- `payable_amount_cents = original_amount_cents * discount_rate / 100`
- `discount_amount_cents = original_amount_cents - payable_amount_cents`
- `points_awarded = payable_amount_cents / 100`，向下取整

已有数据库升级到该结构时，先执行 `scripts/upgrade_phase1_court_assets.sql`，再执行 `scripts/upgrade_phase2_member_accounts.sql`。两个脚本都通过 `information_schema` 判断字段是否存在，可重复执行。
