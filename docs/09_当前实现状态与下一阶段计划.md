# 当前实现状态与下一阶段计划

## 1. 当前代码状态

截至当前阶段，项目已经完成从任务书到可运行业务版本的第六轮落地。当前版本包含用户认证闭环、场地预约闭环、后台基础管理、规则配置、统计分析、操作日志、预约状态自动处理、验证码、找回密码、基础安全增强、后台体验优化和场地资产价格真实化。

已完成内容：

- 后端 Tornado 应用入口、路由和统一 JSON 响应。
- MySQL 连接池、基础查询封装和核心 repository。
- Redis、MySQL、API 健康检查。
- 用户注册、登录、JWT 鉴权。
- 图形验证码，登录、注册和找回密码均需要校验。
- 找回密码两步流程：身份验证后发放短期重置凭证，再提交新密码。
- 当前用户信息查询、资料修改和密码修改。
- 场地列表和后台场地维护。
- 场地资产和价格真实化：场地图片、标签、容纳人数和每小时价格来自数据库。
- 按配置生成场地时间段，支持 `available/reserved/locked/disabled` 状态。
- 预约创建，使用 Redis `SET NX EX` 做并发窗口锁。
- MySQL 时间重叠冲突校验，最终防止重复预约。
- 预约写入使用 MySQL 短事务兜底，事务内锁定用户行、场地行并重新校验每日次数和时间重叠。
- 预约写入时在事务内读取场地价格，并保存价格、时长、原始金额、优惠金额和应付金额快照。
- 我的预约列表和未开始预约取消。
- 管理员用户新增、启用/禁用、角色修改。
- 管理员预约列表、详情和取消预约。
- 管理员公告发布、编辑、显示/隐藏。
- 管理员规则配置查询和更新。
- 后台统计总览、场地使用率、热门时间段和用户活跃度接口。
- 后台统计视图，支持按日期范围查看统计数据。
- 管理员关键写操作日志，包括用户、场地、预约、公告和规则配置。
- 操作日志查询视图，支持按模块、操作人、日期筛选。
- 预约状态自动处理，查询预约和统计前会将已结束 `confirmed` 预约更新为 `completed`。
- 登录返回 access token 和 refresh token，refresh token 存入 Redis 并支持轮换。
- 退出登录会删除 refresh token。
- 登录失败次数使用 Redis 计数，达到阈值后短暂锁定用户名。
- 密码修改、找回密码和管理员重置密码会清理旧 refresh token。
- 默认管理员密码检测和改密提醒。
- 管理员可重置其他用户密码。
- 管理员禁用用户、停用场地前会检查未来有效预约，存在预约时返回冲突并要求先处理预约。
- 后台用户、场地、预约、公告、日志已接入分页和筛选。
- 用户取消预约、管理员取消预约、禁用用户、停用场地、重置密码、修改角色、隐藏公告和保存规则配置均加入二次确认。
- 预约冲突、空状态、加载状态提示已优化。
- Vue3 前端基础布局、路由、Pinia 登录态和 Axios 拦截器。
- 登录页、注册页、个人中心页、场地预约页、我的预约页、后台管理页。
- 忘记密码页，支持验证码、联系方式校验和新密码提交。
- 前端路由守卫：未登录不能访问业务页，普通用户不能访问后台。

## 4. 前端产品化改造状态

本轮按“运动俱乐部预约工作台”概念图一改造用户端视觉。已落地内容：

- 全局外壳改为白色俱乐部侧栏、顶部状态栏和紧凑业务工作区。
- 场地预约页改为三段式产品界面：日期条、场地图片卡片、时间段矩阵和右侧预订清单。
- 场地卡片加入真实感球馆图片、空调开放状态、选中勾选和价格展示。
- 时间段从原单场地按钮列表升级为多场地矩阵，支持查看前 4 个场地的可订、已订、锁定、不可用状态。
- 右侧预订清单展示已选场地、已选时间、费用明细、备注和确认预约操作。
- 侧栏补充会员卡视觉、规划中业务入口和会员状态展示。

概念图一中暂未完成或当前仅为界面占位的功能：

- 会员余额、积分、会员有效期目前是前端静态展示，尚未接入会员账户表和余额流水。
- 天气、通知角标目前是界面展示，尚未接入天气服务和站内通知模块。
- 活动赛事、球友圈、商城、帮助中心入口已按概念图放入侧栏，但当前为禁用状态，尚未建设对应路由和接口。
- 场地价格、图片、标签和容纳人数已接入数据库，预约创建会写入费用快照。
- 优惠券和会员折扣目前只用于预订清单展示，尚未接入真实优惠券、会员等级或结算规则。
- 预约成功仍按当前业务规则直接写入 `confirmed`，没有支付订单、支付状态和支付回调。
- 场地图片当前支持 URL 或项目内置路径，暂不做图片上传。
- 当前一次只提交一个时间段，暂未支持连续多小时、多场地购物车式批量预订。

这些缺口属于“产品化增强”范围，不影响当前认证、场地、预约、后台管理和高并发冲突控制闭环。

产品化增强建议按以下阶段推进，每个阶段独立开发、独立提交，避免一次性引入过多业务变量：

### 4.1 第一阶段：场地资产和价格真实化

状态：已完成。

目标：先让预约页中最核心的场地信息不再是前端静态展示。

范围：

- 场地表增加或复用字段保存每小时价格、场地图片、场地标签和容纳人数。
- 后台场地管理支持维护价格、图片地址、标签和描述。
- 用户端场地卡片读取真实价格和图片。
- 创建预约时写入费用快照，避免后续改价影响历史预约。
- 预约清单中的场地费、合计金额由后端返回或按后端配置计算。
- 新增 `scripts/upgrade_phase1_court_assets.sql`，用于已有数据库幂等升级。

验收标准：

- 不同场地可以展示不同图片和价格。
- 后台修改场地价格后，新的预约使用新价格，历史预约金额不被覆盖。
- `GET /api/courts` 和预约详情能返回前端需要展示的价格和图片字段。
- 预约并发冲突逻辑不受价格字段影响。

### 4.2 第二阶段：会员账户和折扣规则

目标：把侧栏会员卡、余额、积分、会员折扣从视觉占位升级为真实业务数据。

范围：

- 增加会员账户数据：余额、积分、会员等级、有效期。
- 个人中心展示会员账户信息。
- 预约清单接入会员折扣规则，先支持固定折扣或按等级折扣。
- 预约成功后可记录积分变化，先不做复杂积分商城。
- 后台支持查看和调整用户会员状态，关键调整写入操作日志。

验收标准：

- 登录后侧栏会员卡显示当前用户真实余额、积分和有效期。
- 不同会员等级在预约清单中看到不同折扣。
- 预约成功后金额和折扣写入预约记录，后续查询保持一致。
- 管理员调整会员信息有日志记录。

### 4.3 第三阶段：通知、公告详情和帮助中心

目标：优先补齐低风险的信息类功能，让顶部通知和侧栏帮助入口可用。

范围：

- 增加站内通知列表，支持已读/未读状态。
- 顶部通知角标读取真实未读数量。
- 公告列表增加详情页或详情弹窗。
- 帮助中心先做静态规则说明，包括预约、取消、会员、场地使用须知。
- 天气信息先作为可选增强，可以先接入配置值或保留为静态展示。

验收标准：

- 用户能查看通知并标记已读。
- 顶部角标能随未读数量变化。
- 公告内容可以从首页或帮助中心进入详情。
- 帮助中心可解释当前系统的预约规则和取消规则。

### 4.4 第四阶段：活动赛事、球友圈和商城入口

目标：把侧栏中当前禁用的产品入口逐步变成可访问页面，但先控制业务深度。

范围：

- 活动赛事：先支持活动列表、详情和报名，不做复杂赛程编排。
- 球友圈：先支持简单动态列表和发布文本内容，不做复杂社交推荐。
- 商城：先支持商品展示和外部购买说明，不接入真实库存和支付。
- 每个入口都要有空状态、加载状态和权限控制。

验收标准：

- 侧栏入口不再禁用，能进入对应页面。
- 活动报名、动态发布、商品浏览至少完成基础闭环。
- 管理端能维护活动和商品的基础展示信息。
- 不引入影响预约主流程的强依赖。

### 4.5 第五阶段：支付订单和批量预订

目标：最后再处理复杂交易和更高并发的预订场景。

范围：

- 预约创建从直接 `confirmed` 升级为订单流程，可引入 `pending`、支付中、已支付等状态。
- 支持连续多小时选择和多场地批量预订。
- Redis 锁从单时间段扩展到多时间段组合锁，锁释放和过期策略需要统一。
- MySQL 事务层继续作为最终一致性保护，逐条校验所有时间段冲突。
- 支付先可做模拟支付，真实第三方支付放到后续部署前再接。

验收标准：

- 用户可一次选择连续时间段并提交。
- 批量预订任一时间段冲突时，整单能明确失败并释放锁。
- 支付超时订单能释放占用，不影响其他用户预订。
- 高并发下仍然只能有一个用户成功占用同一场地同一时间段。

## 6. 下一阶段建议推送内容

下一阶段建议推送“会员账户和折扣规则”。第一阶段已经把场地资产、价格和费用快照做真，下一步应把侧栏会员卡、余额、积分和预约清单折扣从静态展示升级为真实业务数据。

建议包含以下内容：

1. 增加会员账户数据：余额、积分、会员等级、有效期。
2. 当前用户资料接口返回会员账户信息，侧栏会员卡读取真实数据。
3. 后台用户管理支持查看和调整会员状态，调整写入操作日志。
4. 预约清单接入会员折扣规则，先支持按会员等级折扣。
5. 预约创建时写入折扣金额和应付金额快照。
6. 更新接口文档、数据库设计文档和当前实现状态文档。

完成后应达到：

- 会员卡区域不再使用静态余额、积分和有效期。

- 预约金额、折扣金额和应付金额在创建时固化。
- 当前 Redis 锁和 MySQL 事务冲突控制保持不变。

## 7. 下一阶段暂不建议优先做的内容

以下内容可以继续后置：

- 短信验证码。
- 复杂排班。
- 小程序端。
- 真实第三方支付。
- 复杂库存商城。
- 复杂社交推荐。

原因是这些扩展会增加业务复杂度。当前应在场地资产和价格已经做真的基础上，再逐步扩展会员、通知、活动和交易能力。
