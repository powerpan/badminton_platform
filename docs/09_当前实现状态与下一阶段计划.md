# 当前实现状态与下一阶段计划

## 1. 当前代码状态

截至当前阶段，项目已经完成从任务书到可运行业务版本的主要落地。当前版本包含用户认证闭环、会员账户闭环、会员余额明细、场地预约待支付订单闭环、站内通知、公告详情、帮助中心、后台基础管理、规则配置、统计分析、操作日志、预约状态自动处理、验证码、找回密码、基础安全增强、Element Plus 前端重构、后台体验优化和场地资产价格真实化。

已完成内容：

- 后端 Tornado 应用入口、路由和统一 JSON 响应。
- MySQL 连接池、基础查询封装和核心 repository。
- Redis、MySQL、API 健康检查。
- 用户注册、登录、JWT 鉴权。
- 图形验证码，登录、注册和找回密码均需要校验。
- 找回密码两步流程：身份验证后发放短期重置凭证，再提交新密码。
- 当前用户信息查询、资料修改和密码修改。
- 会员账户信息查询，包含会员等级、有效期、余额、积分、固定折扣和当前实际折扣。
- 会员中心已补充余额明细，可查看预约扣款、预约退款、商城支付、商城退款和后台调整流水。
- 前端应用启动后会刷新当前登录用户资料，避免侧栏会员等级、余额和积分继续显示旧缓存。
- 场地列表和后台场地维护。
- 场地资产和价格真实化：场地图片、标签、容纳人数和每小时价格来自数据库。
- 按配置生成场地时间段，支持 `available/reserved/locked/disabled` 状态。
- 预约创建，使用 Redis `SET NX EX` 做并发窗口锁。
- MySQL 时间重叠冲突校验，最终防止重复预约。
- 预约写入使用 MySQL 短事务兜底，事务内锁定用户行、会员账户行、场地行并重新校验每日次数和时间重叠。
- 预约写入时在事务内读取场地价格，并保存价格、时长、原始金额、优惠金额和应付金额快照。
- 预约写入时会读取当前有效会员等级，按普通、银卡、金卡、钻石固定折扣计算金额，先生成 `pending` 预约和待支付预约订单。
- 创建待支付预约时会扣除当前未过期待支付预约订单占用的余额，防止用户同时保留多笔待支付订单后才在支付环节暴露余额不足。
- 预约余额支付使用 MySQL 事务锁定预约订单、预约和会员账户，扣余额、发积分、订单改为 `paid` 和预约改为 `confirmed` 同成同败。
- 待支付预约订单超时会自动改为 `expired`，释放场地占用。
- 用户取消待支付预约只释放占用；取消已支付预约会退回余额并扣回对应积分。
- 我的预约列表支持待支付预约继续支付和未开始预约取消。
- 管理员用户新增、启用/禁用、角色修改。
- 管理员会员账户调整，支持修改等级、有效期、余额增减、积分增减和调整原因。

- 站内通知列表、未读角标、单条已读和全部已读。

## 4. 前端产品化改造状态

本轮按“运动俱乐部预约工作台”概念图一改造用户端视觉。已落地内容：

- 全局外壳改为白色俱乐部侧栏、顶部状态栏和紧凑业务工作区。
- 场地预约页改为三段式产品界面：日期条、场地图片卡片、时间段矩阵和右侧预订清单。
- 场地卡片加入真实感球馆图片、空调开放状态、选中勾选和价格展示。
- 时间段从原单场地按钮列表升级为多场地矩阵，支持查看前 4 个场地的可订、已订、锁定、不可用状态。
- 右侧预订清单展示已选场地、已选时间、费用明细、备注和确认预约操作。
- 侧栏补充会员卡视觉、规划中业务入口和会员状态展示，并已接入真实会员账户数据。

概念图一中暂未完成或当前仅为界面占位的功能：

- 天气目前仍为静态展示，尚未接入天气服务。
- 顶部通知角标已接入真实未读数，侧栏帮助中心已启用。
- 活动赛事、球友圈、商城入口已启用，具备用户端页面、后台基础维护和对应接口。
- 场地价格、图片、标签和容纳人数已接入数据库，预约创建会写入费用快照。
- 会员等级、余额、积分、有效期和预约折扣已接入真实账户，预约支付成功后扣余额并发积分，取消已支付预约退款并扣回积分。
- 优惠券暂未建设，当前只支持固定会员等级折扣。
- 预约已改为待支付订单流程：创建时写入 `pending`，余额支付成功后改为 `confirmed`；商城也支持会员余额支付订单。
- 场地图片当前支持 URL 或项目内置路径，暂不做图片上传。
- 当前一次只提交一个时间段，暂未支持连续多小时、多场地购物车式批量预订。

这些缺口属于“产品化增强”范围，不影响当前认证、场地、预约、后台管理和高并发冲突控制闭环。

产品化增强建议按以下阶段推进，每个阶段独立开发、独立提交，避免一次性引入过多业务变量：

### 4.1 第一阶段：场地资产和价格真实化

状态：已完成。

目标：先让预约页中最核心的场地信息不再是前端静态展示。

范围：

- 场地表增加或复用字段保存每小时价格、场地图片、场地标签和容纳人数。
- 后台场地管理支持维护价格、图片地址、标签和描述。
- 用户端场地卡片读取真实价格和图片。
- 创建预约时写入费用快照，避免后续改价影响历史预约。
- 预约清单中的场地费、合计金额由后端返回或按后端配置计算。
- 新增 `scripts/upgrade_phase1_court_assets.sql`，用于已有数据库幂等升级。

验收标准：

- 不同场地可以展示不同图片和价格。
- 后台修改场地价格后，新的预约使用新价格，历史预约金额不被覆盖。
- `GET /api/courts` 和预约详情能返回前端需要展示的价格和图片字段。
- 预约并发冲突逻辑不受价格字段影响。

### 4.2 第二阶段：会员账户和折扣规则

状态：已完成。

### 4.5 第五阶段：预约支付订单（已完成，批量和部署验收后置）

目标：先处理预约侧支付订单，批量预订、自动化测试和部署验收暂不纳入本轮。

范围：

- 预约创建从直接 `confirmed` 升级为 `pending` 预约和 `pending` 预约订单。
- 新增 `reservation_order` 表和 `PUT /api/reservation-orders/{id}/pay` 余额支付接口。
- 支付接口在一个 MySQL 事务内锁定订单、预约和会员账户，保证扣款、发积分、订单支付和预约确认同成同败。
- 待支付订单过期自动释放占用。
- 用户端预约页支持创建待支付订单后立即支付；我的预约页支持待支付继续支付或取消。
- 管理端预约列表支持查看和取消待支付预约。

验收标准：

- 创建预约后不会立即扣款，支付成功后才扣款并确认预约。
- 支付超时订单能释放占用，不影响其他用户预订。
- 同一预约订单重复支付不会重复扣款。
- 高并发下仍然只能有一个用户成功占用同一场地同一时间段，且不会出现扣款成功但预约未确认的半成功状态。
