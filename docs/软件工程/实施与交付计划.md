## 3. 变更控制与进度记录

业务基线为用户确认的完整时段原价、前台设备收款、商城支付后取货码、内部模拟、正额代充值、管理员全量查询。实现中遇到名称、索引、组件拆分等选择可按设计推进并同步文档；若改变收费、权限、退款资格或客户操作路径，应清楚记录变化及影响，不能借技术实现静默修改需求。

每批记录：开始/完成日期、涉及 FR 编号、代码提交、数据迁移版本、检查结果、未测项与遗留缺陷。完成代码、通过本地验收、Git 推送、实际环境迁移、部署可访问是不同状态，分别登记。

不预填“已通过”，不在没有实现时沿用历史测试数量。没有实际测试结果的工作只能标记“实现完成，待验收”。

## 4. 主要风险与应对

| 风险 | 触发场景 | 设计/验证措施 |
| --- | --- | --- |
| 散客丢失或误扣前台余额 | 沿用客户非空和客户=操作人的代码 | 可空客户与经办字段；LEFT JOIN；前台余额不变断言 |
| 模拟渠道仍被余额限制 | 沿用预约占款和商城核价 | 渠道分支与新旧占用互斥求和，零余额模拟付款测试 |
| 退款凭空增加余额 | 沿用现有统一退余额 | 统一按原付款渠道；改期多次退差/取消累计校验 |
| 超卖或重复占场 | 只依赖 UI/Redis 或各入口锁顺序不同 | 共享 DB 事务边界；商品行/场地行锁；并发与过期竞争测试 |
| 充值/取货重复处理 | 网络重试或旧入口绕过 | 请求号+业务唯一约束+同事务效果；旧入口纳入服务 |
| 历史数据被误解释 | 默认值补付款/维修/到场 | 保留事实与未知标记；迁移前后核对，分类人工确认 |
| 统计虚增 | 充值、消费、账户流水直接相加 | 独立指标来源、关联去重和 100 元样例对账 |
| 页面仍有模板感或操作繁琐 | 四角色复用同一巨大后台 | 前台排期收银、维修任务列表；保持 BF 视觉及统一控件状态 |

运行基线按 [当前部署说明](../部署说明.md)。其中已补阶段八预览与升级步骤；新增资金流程已通过分批本地验证；D06 本地验收已登记；实际环境、验证码与设备验收仍待完成。

## 6. 迁移与交付顺序

1. **准备可审查版本**：实现 D01–D06，补全测试，记录待办；检查 Git diff 中没有私密配置或无关资料。
2. **隔离迁移演练**：旧结构样例、二次迁移、新库对照、故障恢复和原记录守恒；完成备份恢复试验。
3. **本地验收**：测试计划中的业务、权限、页面和性能用例；输出报告，保留未测项。
4. **源码交付**：按实际授权提交和推送，记录远端 commit；推送不等于运行环境已升级。
5. **环境升级**：在停止业务写入的窗口备份、迁移、部署新后端与前端、验证角色/场地/交易查询；准确登记环境与版本。
6. **入口交付**：确认正式 HTTPS URL、深链接刷新、手机与微信内页面；提供可复制链接及其用途说明。
7. **收尾**：交付操作手册、测试报告、迁移日志、备份定位与恢复说明、已知限制；实际客户试用问题进入缺陷列表。

微信公众号只作为以后放置网站链接的位置。本项目交付网址和说明，不包含代登录公众号、创建菜单、微信审核或发布文章。

## 7. 回退与完成定义

回退策略遵循 [数据库设计](数据库设计说明书.md)：新增交易写入后不能直接使用只识别两角色和余额支付的旧代码；遇到问题先停止写入、保存现场，优先修复前进。恢复备份前明确备份后数据如何保留和恢复，不直接删除新增业务表。

完成定义：每条 FR 有实现和验收记录，接口和数据库文档反映实际结构，关键失败路径有证据，管理员全量记录可核对。未获得实际部署或设备证据时，交付说明只写本地完成，不写已上线或已通过微信实机验证。
