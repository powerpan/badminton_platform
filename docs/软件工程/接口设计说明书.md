## 1. 统一约定

- 保留 `/api` 前缀与 `Authorization: Bearer …`；服务端按数据库中的当前用户状态和角色授权。
- 沿用响应壳 `{ "code": 0, "message": "success", "data": ... }`，错误 `code` 非零；金额统一为 `*_cents` 整数分。
- 日期 `YYYY-MM-DD`，时段 `HH:MM`，新增时间戳为带 `+08:00` 的 ISO 8601；响应提供 `server_now` 和 `expires_at` 供倒计时，服务器决定是否过期。
- 修改型操作在 JSON 请求体传 `request_key`，不新增自定义请求头；参数摘要由服务端计算。不能信任客户端的角色、经办人、折扣、支付成功标志。
- 分页列表使用 `items/total/page/page_size`；默认 20、最大 100，财务日期跨度第一版最多 366 天。筛选和汇总使用同一条件，稳定按发生时间与记录身份排序。
- 旧调用字段保留兼容需明确测试；新增字段不能静默改变支付渠道。旧客户端省略渠道只保留原余额语义，不能默认为模拟支付宝。

| HTTP 状态 | 场景 | 页面处理 |
| --- | --- | --- |
| 400 | 参数、金额、时间段、请求号不合法 | 保留输入并提示修正 |
| 401 | 未登录或会话失效 | 登录后回到原业务入口 |
| 403 | 角色或资源范围禁止 | 显示权限说明，不重试写入 |
| 404 | 资源不存在或无权识别的他人订单 | 清除旧详情，返回列表 |
| 409 | 价格/版本变更、占用冲突、已过期、非法状态、请求号参数冲突 | 查询原单或重新报价，禁止自动按新金额付款 |
| 500/503 | 服务异常或依赖不可用 | 不宣称付款失败；先查单确认，再使用原请求号重试 |

同请求号、同参数且已成功，返回原成功对象；同号不同参数为 409。相反业务动作（已取货后退款）即使换请求号也必须拒绝。错误响应通过既有非零 code 与明确 message 表达；若实现新增机器可读错误原因，需同步 `ApiError`、前端与此文档。

当前散客接口的 `request_key` 为 8–64 位 ASCII 字母、数字或 `_ . : -`；创建的唯一范围为经办人，操作回执范围为支付单+经办人。同号回执返回提交时的结果；需要最新状态时查详情。散客支付实际状态为 `pending/succeeded/canceled/expired/refunded`，原预约订单仍用 `pending/paid/canceled/expired`。`opened_at` 只在初次开场付款成功时写入，续场不伪造已开始时间。

管理员取消父场次前须先处理仍有效的后续续场；已结束、已有到场结论的订单不能退款。退款保留原金额与 `paid_at`，有正额时新增 `payment_refund`，零价取消不造零额退款。前台没有已付退款权限。

## 4. 请求与响应示例

示例为设计样例，ID 与金额不指向现有业务数据。假定测试服务器时间为 2026-10-01 14:10，时段为 60 分钟，单价 120 元。

创建散客订单：

```json
{
  "court_id": 1,
  "reserve_date": "2026-10-01",
  "start_time": "14:00",
  "end_time": "15:00",
  "guest_name": "演示散客",
  "expected_amount_cents": 12000,
  "request_key": "demo-walkin-001"
}
```

拟返回：

```json
{
  "code": 0,
  "message": "待收款",
  "data": {
    "reservation_id": 101,
    "source": "walk_in",
    "billing_start": "2026-10-01T14:00:00+08:00",
    "billing_end": "2026-10-01T15:00:00+08:00",
    "opened_at": null,
    "payment": {
      "id": 201,
      "amount_cents": 12000,
      "pay_method": "mock_alipay",
      "is_simulated": true,
      "status": "pending",
      "expires_at": "2026-10-01T14:25:00+08:00"
    },
    "server_now": "2026-10-01T14:10:00+08:00"
  }
}
```

向该支付单提交模拟确认只需要请求号；金额和经办人从后端订单与当前身份获取。成功结果返回 `paid_at`、业务状态和原编号。为已有会员创建充值单也必须先查明确客户，不能用散客姓名猜测账户。

## 5. 契约验收与兼容检查

- 逐条验证方法、路径、授权、字段单位、状态和错误分支；通配 ID 路由排在静态子路径之后，避免 `quote/my` 被当作订单 ID。
- 新支付服务必须接管旧扣款、完成、退款路径，否则新页面正确也可能被旧接口重复处理。
- 用户可见 `pay_method` 标签区分“储值余额”和“模拟支付宝”；财务中的未知历史证据单独显示，不能使用默认标签掩盖缺失。
- 角色测试同时覆盖页面与 HTTP；刷新页面、退出重登、角色即时变更后重新检查接口。
- 请求失败后，先查单再决定是否创建新单；禁止前端靠本地布尔值认定资金已成功或失败。

所有契约在 [测试计划](测试与验收计划.md) 中以角色、并发、旧报价、重复请求、超时与回滚用例验收。尚未生成 OpenAPI 文件，本文不冒充可执行接口描述。

### D05 代储值实际契约（2026-09-24，已通过本地隔离验证）

- 先以完整用户名或完整登记联系方式精确查询已有客户账户，禁止空查询或模糊列出会员。只返回 ID、用户名、昵称、脱敏联系方式、当前余额；不返回邮箱、积分和会员等级。目标沿用客户角色集合（普通用户和兼具消费权限的管理员），工作人员账户及禁用账户不可充值。
- 前台仅查看/继续自己创建的充值工作单，管理员可查全部并接续操作；创建经办人和实际收款经办人分别保留。第一版不新增用户自助充值、充值退款或负数冲抵；客户从本人账户流水查看入账。
- `GET /api/frontdesk/recharge-customers?query=...` 精确查客户；`POST /api/frontdesk/recharges` 仅接收 `user_id/amount_cents/request_key`。创建与付款时均检查正整数分和账户上限，待付充值不预增余额、不增加等级或积分；超时复用当前付款期限配置。
- `GET /api/frontdesk/recharges` 支持日期范围、状态、完整充值/支付单号和分页；`GET /api/frontdesk/recharges/{id}` 查当前状态/支付/收款后余额凭证；`POST /api/frontdesk/recharges/{id}/cancel` 仅撤销未付单。管理员另有对应只读 `/api/admin/recharges` 和详情入口。
- 充值调用已有支付单的模拟成功/失败接口，前台/管理员收款，普通客户即使是充值受益人也不能从支付接口模拟自助充值。成功事务同时写收款、唯一 `staff_recharge` 账户效果、通知、审计和操作回执；相同请求重试不重复入账。
- 充值详情含创建者快照、目标客户快照、`payment_id/payment_no/payment_status`，以及成功后的 `credit`（入账前/后余额、实际经办、时间）；列表含 `server_now`。统一支付查询返回 `business_type=recharge` 和相同客户/到账凭证。交易类型 `staff_recharge` 由本人流水提供，关联充值及支付 ID。完成依据与环境限制见开发记录。

### D05 全部订场查询契约（2026-09-24，已通过本地隔离验证）

- 保留现有日期（场次日期）、场地、状态、分页与 `username` 参数；客户检索同时匹配用户名、昵称、登记联系方式、散客姓名及散客联系方式，按普通文本包含匹配，`%` 和 `_` 不作为通配符。
- 增加 `source=online/walk_in/walk_in_extension`、`pay_method=balance/mock_alipay`、`operator`（开单经办用户名快照或当前用户名/昵称，普通文本包含）、`order_no`（完整预约号、业务订单号、任一关联支付号或退款号）。渠道包括初始订单及关联补差支付，筛选不重复返回预约。
- 列表的 `items/total/server_now` 来自同一数据库快照；稳定按场次日期、开始时间、ID 倒序。分页默认 10、最大 100。空条件查询全部，历史记录保留。
- 详情保留原字段，新增 `chain`、`payments`、`refunds`、`account_transactions`、`changes` 和 `server_now`，在同一快照返回。续场链含根场次与全部子场次（包括取消/过期），可逐笔进入详情。支付区分开单人与首次实际成功收款命令的经办人；缺少原始凭据时不以创建人代填收款人。
- 详情不返回请求摘要、幂等键或内部命令完整快照。历史无统一支付单时明确提示查阅原账户流水，不能由预约状态推定真实付款或到场。列表和详情仅管理员可读；前台仍使用散客工作台接口。

### D05 全局流水实际契约（2026-09-24，已通过本地隔离验证）

- `GET /api/admin/transactions`：`date_from/date_to` 按资金记录发生日（含结束日），默认最近 30 天，最多 366 天；`business_type` 为 reservation/walk_in/walk_in_extension/shop/recharge/reschedule/adjustment，`entry_type` 为 collection/refund/recharge/adjustment/points/unverified；渠道 balance/mock_alipay/manual/unknown；状态 pending/succeeded/refunded/canceled/expired/recorded/unverified。另支持客户文本 `customer`、经办文本 `operator`（成功收退款取实际经办，未收款取开单人）、完整单号 `order_no` 与分页（默认 20、最大 100）。
- 记录身份为 `record_type + record_id`，来源 payment/refund/account/legacy_reservation/legacy_shop。已关联统一收退款的账户流水不重复列为第二笔资金交易，原账户记录从详情追溯；未关联的历史余额流水、人工调整及纯积分仍可查看。没有付款凭据的历史已付业务列为 unverified，金额只供核查，不计入已确认汇总。
- 付款发生时间取成功时间；未成功单取关闭或创建时间；退款取实际退款时间；账户流水取自身时间。付款全额退回后仍保留原成功收款，退款另列负数记录。列表金额表示收款/消费正数、退款负数；人工调整使用账户余额增减方向，不代表收入。
- `summary` 与列表筛选相同，覆盖全部匹配记录，且与分页处于同一只读快照。分别返回渠道收款、渠道退款、渠道净额、其中储值充值、余额消费、余额退回、消费结算净额、人工调增/调减、待核对笔数；充值是渠道收款子项，不能相加。纯积分不算资金收入。
- `reconciliation` 返回 `accounts/without_history/mismatches/issues`；客户范围来自完整筛选集合，核对这些客户的全部账户流水及当前余额、积分。检查每笔前后差额、与前一笔的衔接及末余额；异常明细最多 20 个账户。第一笔前余额作为历史期初，不推定外部付款事实。无流水单列，不能称核对成功。此查询与汇总、分页使用同一只读一致快照。
- `GET /api/admin/transactions/{record_type}/{id}` 返回选中来源记录、对应业务基本信息、相关支付/退款、原账户流水和改期记录；不返回密码、令牌、取货码、请求摘要或内部命令快照。已收款记录的经办按首次成功操作回执识别，不能拿创建人代填；人工调整/退款按对应不可变记录识别。
- 原运营看板的场次核对改为统一支付净额优先、历史账户流水其次；缺付款依据单列待核对，不能把模拟支付误判为余额短缺。计费占用继续包含续场时长，到场率按首场/线上预约统计，续场不重复作为新到店人数。
