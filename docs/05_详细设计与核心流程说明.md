# 详细设计与核心流程说明

## 1. 文档目的

本文档用于说明 BF羽毛球馆管理平台的核心业务流程和关键实现细节。重点覆盖登录认证、预约创建、Redis 锁、预约取消、超时释放、管理员维护和系统健康检查等流程。

## 2. 后端分层设计

后端基于 Tornado 实现，建议采用分层结构，避免所有逻辑写在 Handler 中。

```text
Request
  -> Handler 请求处理层
  -> Service 业务逻辑层
  -> Repository 数据访问层
  -> MySQL / Redis
```

### 2.1 Handler 层

职责：

- 接收 HTTP 请求。
- 解析请求参数。
- 调用认证和权限校验。
- 调用 Service 层。
- 返回统一 JSON 响应。

Handler 层不应写复杂业务逻辑。

### 2.2 Service 层

职责：

- 处理核心业务规则。
- 控制事务边界。
- 处理 Redis 锁。
- 判断预约冲突。
- 写操作日志。

预约、取消、管理员维护等关键逻辑应放在 Service 层。

### 2.3 Repository 层

职责：

- 封装 MySQL 查询。
- 提供清晰的数据访问方法。
- 避免 SQL 散落在 Handler 和 Service 中。

### 2.4 Utils 层

职责：

- JWT 生成和解析。
- 密码加密和校验。
- 时间格式处理。
- 统一响应封装。
- 参数校验辅助函数。

## 4. 登录认证流程

### 4.1 注册流程

```text
用户填写注册表单
  -> 前端校验必填项
  -> 获取并填写图形验证码
  -> POST /api/auth/register
  -> 后端校验 Redis 中的验证码
  -> 后端校验用户名是否重复
  -> 后端加密密码
  -> 写入 user 表
  -> 返回注册成功
```

异常处理：

- 用户名为空：返回参数错误。
- 用户名重复：返回业务冲突。
- 密码长度不足：返回参数错误。
- 验证码错误或过期：返回参数错误，验证码失效后需重新获取。

### 4.2 登录流程

```text
用户输入用户名、密码和验证码
  -> POST /api/auth/login
  -> 后端校验 Redis 中的验证码
  -> 检查用户名是否处于短暂锁定状态
  -> 后端查询用户
  -> 校验账号状态
  -> 校验密码
  -> 生成 access token 和 refresh token
  -> refresh token 写入 Redis
  -> 更新 last_login_at
  -> 返回 token 和用户信息
```

JWT 建议字段：

```json
{
  "user_id": 1,
  "username": "zhangsan",
  "role": "user",
  "exp": 1770000000
}
```

Refresh token 设计：

- access token 负责接口鉴权。
- refresh token 存在 Redis 中，支持退出登录删除和刷新时轮换。
- 修改密码、找回密码和管理员重置密码后，会删除该用户旧 refresh token。

### 4.3 找回密码流程

```text
用户输入用户名、联系方式和验证码
  -> POST /api/auth/password-reset/request
  -> 后端校验验证码
  -> 后端校验用户名和联系方式
  -> Redis 写入短期 password reset token
  -> 前端进入新密码提交步骤
  -> POST /api/auth/password-reset/confirm
  -> 后端校验 reset token
  -> bcrypt 加密新密码
  -> 更新 user.password_hash
  -> 删除 reset token 和旧 refresh token
  -> 返回密码重置成功
```

当前版本没有短信或邮件服务，因此重置凭证由接口返回给前端完成本地演示闭环。后续如果接入短信或邮件，只需要把 `reset_token` 的交付方式替换掉，Redis TTL、密码更新和旧 token 清理逻辑可以继续复用。

### 4.4 权限校验流程

```text
请求进入 Handler
  -> 读取 Authorization 请求头
  -> 解析 JWT
  -> 查询或确认用户状态
  -> 校验接口所需角色
  -> 通过后执行业务逻辑
```

校验失败情况：

- 无 token：返回 401。
- token 过期：返回 401。
- 用户被禁用：返回 403。
- 角色不足：返回 403。

## 5. 预约创建流程

预约是系统中最关键的流程，需要同时处理参数校验、业务规则、Redis 锁和 MySQL 记录。

### 5.1 预约请求参数

核心参数：

- `court_id`
- `reserve_date`
- `start_time`
- `end_time`
- `remark`

### 5.2 预约前校验

创建预约前需要校验：

- 用户已登录。
- 用户状态为启用。
- 场地存在且启用。
- 日期格式正确。
- 预约日期不早于当前日期。
- 预约日期不超过可提前预约天数。
- 结束时间晚于开始时间。
- 预约时长不超过最大预约时长。
- 用户当天预约次数不超过限制。

### 5.3 Redis 锁设计

Redis 锁 key 建议：

```text
reservation:lock:{court_id}:{reserve_date}:{start_time}:{end_time}
```

示例：

```text
reservation:lock:1:2026-05-15:09:00:10:00
```

锁 value 建议：

```text
user_id:reservation_request_id
```

加锁命令语义：

```text
SET key value NX EX ttl_seconds
```

含义：

- `NX`：只有 key 不存在时才设置成功。
- `EX`：设置过期时间。
- `ttl_seconds`：来自系统配置，默认 300 秒。

### 5.4 预约主流程

```text
用户提交预约
  -> 校验请求参数
  -> 校验用户状态
  -> 校验场地状态
  -> 读取系统配置
  -> 生成 Redis 锁 key
  -> Redis SET NX EX 尝试加锁
  -> 如果加锁失败，返回该时段正在预约或已被占用
  -> 查询 MySQL 是否已有有效预约
  -> 如果有冲突，释放 Redis 锁并返回重复预约
  -> 写入 reservation 表
  -> 返回预约成功
```

### 5.5 MySQL 冲突校验

加锁成功后仍需查询 MySQL，原因是 Redis key 可能过期或被清理，数据库才是最终数据来源。

冲突条件：

- 同一 `court_id`。
- 同一 `reserve_date`。
- 时间段重叠。
- 状态为 `pending` 或 `confirmed`。

时间段重叠判断：

```text
new_start < old_end AND new_end > old_start
```

### 5.6 写入预约记录

基础版本可直接写入：

```text
status = confirmed
```

如果要体现超时确认流程，可采用：

```text
status = pending
```

然后在规定时间内确认。超时后改为 `expired`。

### 5.7 异常回滚

如果加锁成功但 MySQL 写入失败，需要释放 Redis 锁。

```text
Redis 加锁成功
  -> MySQL 写入失败
  -> 删除 Redis 锁
  -> 返回系统错误
```

删除锁时应校验 value，避免误删其他请求的锁。

## 6. 预约取消流程

### 6.1 普通用户取消

```text
用户点击取消预约
  -> 前端弹出确认框
  -> PUT /api/reservations/{id}/cancel
  -> 后端校验登录态
  -> 查询预约记录
  -> 校验预约属于当前用户
  -> 校验预约状态允许取消
  -> 校验是否超过取消时间限制
  -> 更新状态为 canceled
  -> 写入取消时间
  -> 返回成功
```

用户不能取消：

- 不属于自己的预约。
- 已取消预约。
- 已完成预约。
- 已过期预约。
- 超过取消时间规则的预约。

### 6.2 管理员取消

管理员可以取消异常或违规预约。

```text
管理员选择预约记录
  -> 填写取消原因
  -> 后端校验 admin 角色
  -> 更新预约状态
  -> 写入操作日志
  -> 返回成功
```

## 7. 超时释放流程

任务书要求 Redis 实现预约时间段锁定与超时自动释放。基础实现可以分为两种方式。

### 7.1 方式一：Redis key 自动过期

适用场景：预约只是短暂锁定，未写入正式预约记录。

流程：

```text
用户选择时段
  -> Redis 加锁，设置 TTL
  -> 用户在 TTL 内确认
  -> 确认后写入 MySQL
  -> 未确认则 Redis key 自动过期
```

优点：

- 实现简单。
- Redis 自动处理释放。

缺点：

- 如果前端不做“确认预约”步骤，用户感知不明显。

### 7.2 方式二：pending 预约加定时扫描

适用场景：创建预约后先进入待确认状态。

流程：

```text
创建预约
  -> MySQL 写入 pending
  -> Redis 写入 pending key 并设置 TTL
  -> 用户确认后改为 confirmed
  -> 后台任务扫描超时 pending 记录
  -> 超时记录改为 expired
```

优点：

- 数据库中可以追踪超时预约。
- 适合后续接入支付。

缺点：

- 实现比方式一复杂。
- 需要后台定时任务。

### 7.3 本项目建议

根据任务书范围，建议基础版本采用：

- 提交预约时 Redis 加锁。
- MySQL 最终写入 `confirmed`。
- Redis key 设置短 TTL，用于并发窗口控制。
- 如果后续需要“待确认”页面，再扩展 `pending` 状态和后台扫描。

这样能满足防重复预约要求，也更适合毕业设计或课程项目按期完成。

## 8. 管理员维护流程

### 8.1 用户管理

```text
管理员进入用户管理页
  -> 查询用户列表
  -> 执行新增、禁用、启用、改角色
  -> 后端校验 admin 角色
  -> 更新 user 表
  -> 写入 operation_log
```

注意事项：

- 不允许管理员禁用自己，避免后台无法继续操作。
- 修改角色需要记录日志。
- 禁用用户后，该用户后续请求应被拒绝。

### 8.2 场地管理

```text
管理员进入场地管理页
  -> 查询场地列表
  -> 新增或编辑场地
  -> 启用或停用场地
  -> 写入 operation_log
```

停用场地前建议检查是否存在未来有效预约。如果存在，应提示管理员确认。

### 8.3 公告管理

```text
管理员发布公告
  -> 后端保存公告标题和内容
  -> 状态设置为发布
  -> 用户端公告列表可见
```

删除公告可以采用：

- 物理删除。
- 或将 `status` 改为隐藏。

为了保留操作痕迹，建议采用隐藏状态。

### 8.4 系统规则配置

```text
管理员修改配置
  -> 后端校验配置 key 是否存在
  -> 校验配置值是否合法
  -> 更新 config 表
  -> 清理或刷新 Redis 中的配置缓存
  -> 写入 operation_log
```

配置值需要做类型校验。例如预约超时时间必须是正整数。

## 9. 数据统计设计

基础统计可以直接从 MySQL 查询获得。

### 9.1 预约总览

统计项：

- 总预约数。
- 今日预约数。
- 已取消预约数。
- 活跃用户数。

### 9.2 场地使用率

计算方式：

```text
场地使用率 = 已预约时间段数量 / 可预约时间段总数量
```

基础版本可以按天统计。

### 9.3 热门时间段

按 `time_slot` 分组统计预约数量，倒序返回。

### 9.4 用户活跃度

按 `user_id` 分组统计预约数量，取前若干名。

## 10. 操作日志设计

需要记录的操作：

- 管理员新增、禁用、启用用户。
- 管理员修改角色。
- 管理员新增、编辑、停用场地。
- 管理员取消预约。
- 管理员发布、编辑、隐藏公告。
- 管理员修改系统配置。

日志内容包括：

- 操作人。
- 操作模块。
- 操作类型。
- 操作目标。
- 操作时间。

- 详细内容。

## 11. 健康检查设计

健康检查接口用于管理员查看系统状态。

检查内容：

- Tornado 服务是否正常响应。
- MySQL 是否可以执行简单查询。
- Redis 是否可以 ping 通。

推荐检查方式：

```text
MySQL: SELECT 1
Redis: PING
API: 当前接口能正常返回
```

## 12. 关键风险与处理

### 12.1 重复预约风险

风险：多个用户同时提交同一时间段预约。

处理：

- Redis `SET NX EX` 加锁。
- MySQL 再做一次有效预约检查。
- 数据库层增加合理索引。

### 12.2 锁释放风险

风险：业务异常导致 Redis 锁未释放。

处理：

- Redis 锁必须设置 TTL。
- MySQL 写入失败时主动释放锁。
- 删除锁时校验 value。

### 12.3 权限绕过风险

风险：前端隐藏按钮但用户直接调用后台接口。

处理：

- 后端所有管理员接口都校验 `admin`。
- 普通用户接口校验数据归属。

### 12.4 配置错误风险

风险：管理员输入非法配置值。

处理：

- 后端校验配置类型和范围。
- 关键配置修改写入日志。
