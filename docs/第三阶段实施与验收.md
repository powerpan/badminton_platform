# 第三阶段：推荐与运营闭环

2026-09-16，C01–C05 及用户追加的 C06 已完成本地实现和隔离验收；沿用第二阶段视觉系统。

## 业务与迁移决策

- 新增维护、到场和改期历史三张扩展表，提供幂等升级脚本并同步新库初始化。旧预约不回填虚构到场事实，不重算历史费用。
- 维护与下单、改期在同一场地锁下检查半开区间冲突；维护不自动取消已有预约。
- 核销允许开始前 30 分钟至结束前；未到场只在结束后由管理员确认。同结论重复提交幂等，不允许静默覆盖相反结论。
- 改期仅用于未开始、未核销、具有可核对余额支付流水的已确认预约。待支付预约先取消重订；缺少支付依据的旧预约不开放改期。
- 改期先报价再确认；保留预约和订单编号，记录版本和唯一请求号。新金额使用目标日期的会员权益与当前场地价格；补差尊重其他待支付占用，退款和积分差额进入流水。
- 改期、金额、积分、历史、站内通知在同一事务提交；冲突、余额不足、旧报价或异常时整体回滚，原预约保留。
- 单用户写事务先锁用户，再按编号锁场地；预约和会员账户随后锁定。维护不锁用户，以场地锁作为占用修改的共同边界。
- 当前业务库只应用验证后的新增表迁移；交易与并发实验在独立新库执行。无 Git 推送或外部部署。

## 推荐算法

统一使用后端有效时段（预约、维护及临时锁均不可选）；前缀和判断连续窗口。硬约束为日期、最早开始、时长和可用性；候选按开始时间偏差、场地偏好、金额、短碎片数量、场地编号稳定排序，最多三个。明确是可解释启发式，不声称全局最优。推荐不占位，提交再次检查。

实验使用可重复生成数据，对照朴素窗口扫描检查候选合法性和排序；分别记录不同场地数、时间粒度、占用密度的候选生成耗时。操作体验比较手动选两格与直接应用推荐，不将本地模拟等同真实用户研究。

## 经营看板设计

分析任务是每日变化、时段比较、取消与到场记录、实际余额收支核对。在现有运营总览内增加一个独立组件，最多两个轻量 DOM 条形图，不引入新图表依赖；每日趋势同时提供数据表，时段按占用分钟展示，直接标注数值，零数据明确显示。

日期范围沿用页面控件并保存于 URL；图形由 Vue 和 CSS 渲染，绿色条表示预约，退款与取消使用文字及数值说明。手机图表单列，表格自身滚动。范围最多 366 天，加载、失败、重试及数据更新时间可见。预约指标按场次日期；资金指标按流水发生日期，两种口径分别标注。资金净额用扣费、退款和改期差额计算，不从订单当前状态猜收入。

## 结果

### 实现与验证

- 后端累计 **32 项单元测试**，前端 **6 项逻辑测试**，TypeScript 检查与 Vite 生产构建通过。
- `backend/tests/integration_operations.py` 在每次创建的新库执行 **13 组集成场景**，包括升级旧结构两次、补差/退差/零差、重复请求、旧版本、价格变化、支付凭据缺失、所属用户、余额限制、两类抢占竞争、维护释放、到场幂等及完整回滚；默认结束后仅删除它创建的新库。
- 回滚场景在金额、历史和通知已经写入而事务尚未提交时注入异常，逐项对比原预约、账户、流水、历史及通知，均保持原状。余额和积分另与流水合计核对。
- 业务库只新增三张表，迁移前后预约数/费用总额、会员数/余额/积分合计一致。浏览器的下单、改期、到场和维护操作全部发生在独立库及独立 Redis；未对现有业务余额做交易实验。
- 浏览器通过安装的 Chrome + Playwright 检查 1440×1000、768×1000、390×844。没有 Browser 插件专用技能，采用本地浏览器工具运行真实 Vue 页面；正常流程没有前端运行错误，页面没有持续横向溢出，矩阵和表格在自己的容器内滚动。
- 页面实测：两小时推荐应用、维护时段禁选与原因、释放后恢复、报价与改期、改期历史、重复 HTTP 提交没有新增历史、到场核销、确认未到场、经营日期 URL 刷新恢复、空范围、503 保留旧数据并重试恢复。普通用户访问维护/核销/经营接口均为 403，匿名推荐为 401。
- C06 共检查 **15 个表单状态、72 个输入控件**：登录、注册及错误状态、密码找回、预约/推荐、会员资料、商城筛选、经营日期、维护/新增场地/改期抽屉。鼠标与键盘 Tab 焦点均正常，改期提交期间的禁用控件也没有内层边框。测试中的 400/401/403/503 均为明确的负例。

### 多重边框的原因和修复

Element Plus 已由 wrapper 绘制一层边框。旧 `.summary-actions input` 等原生表单规则又给内部 input 增加边框/阴影，通用 `[tabindex]:focus-visible` 再增加外轮廓，形成截图中的多层框。现在原生规则排除 Element Plus 内部控件，组件使用自身焦点样式；按钮、链接和原生控件仍保留键盘焦点提示。另修正改期历史与预约列表同名 CSS 类造成的布局串扰。

### 推荐实验结果

固定种子生成 1/10/50/200 场地、15/60 分钟格、10%/30%/70% 占用，共 **24 种配置，每种 30 次**。全配置纯候选计算的最大中位数 **12.760 ms**，最大 P95 **14.698 ms**；200 场地 × 15 分钟格共 9,600 格，在 30% 占用时中位数 **4.668 ms**，P95 **5.010 ms**。原始记录见 [recommendation-benchmark.json](recommendation-benchmark.json)。

正确性用 180 组固定种子样例（每组四场地，覆盖三种粒度和两种时长）与朴素扫描比较完整候选集合；另验证稳定排序及同时间同价格下优先保留两格空档而不是单格碎片。前缀和扫描为 O(场地数 × 槽数)，随后对候选排序；不将整段排序误称为线性复杂度。

实际页面中，候选列表出现后一次点击可应用连续两格，手选需要两次；推荐前仍有设置偏好和查询的成本，所以没有据此宣称完整流程更快或具有真实用户研究结论。上述计时只含 Python 内存计算，不含 MySQL、Redis、HTTP 或页面延迟，也不是并发压测。

### 已知限制

- 当前规则是明确、可解释的启发式；推荐不锁位，最终提交仍可能因其他用户抢占而失败。
- 缺少可核对支付流水的历史预约不能在线改期；没有追溯补写历史到场、费用和积分。
- 到场结论只允许幂等重复，相反结论拒绝；本阶段没有新增管理员纠错流程。
- 预订率以当前场地、营业规则和有效维护计算容量，未还原历史营业规则与历史维护版本；它不代表实际使用率。
- 主 JS 仍约 1.10 MB（gzip 366.77 KB），保留体积提示及依赖 PURE 注释警告，没有通过调高阈值掩盖。Python 3.14 下 Tornado 有既有弃用提示。
- 只验证本地 Chrome；未进行真实业务库资金交易、跨浏览器/真实设备验收、长时间压力测试、Git 推送或外部部署。

## 追加修复：后台变更后的结算信息

用户报告商城后台改价后，不刷新客户端仍按旧金额弹出确认。复现进一步确认：原实现确认框沿用购物车快照，但后端使用最新价格扣款，存在确认金额与实际扣款不同的问题。

- 商城每次付款先向 `/api/shop/orders/quote` 核对最新商品价格、库存、上架状态和可用余额。价格变化时更新购物车并在确认框提示；核价失败不能进入付款。
- 提交携带逐项确认单价，后端在商品行锁内比对。即使确认框打开后再次改价，也返回 409，订单、库存、余额和流水不变；降价及多商品涨跌相抵但总额相同的情况同样需要重新确认。旧客户端缺少确认价格会被拒绝。
- 商城可用余额统一扣除未过期的待支付预约占用。按钮不会因本地旧余额直接禁用，后台充值后可再次核价；库存不足或下架保留原购买数量并明确提示。
- 预约刷新时间段时同步场地信息和会员资料。提交前重查，金额变化先展示新金额、等待再次确认；事务内再次校验确认金额，防止最后一刻改价或调整会员权益。推荐和表单在提交期间不能改变当前选择。
- 待支付预约已经锁定订单金额，后续场地调价不追改该订单。付款前查询当前订单状态，避免沿用已取消或过期的列表项。
- 改期遇到 409 或重新报价失败时撤下旧报价，重新计算后才能确认；活动报名失败后刷新人数和可报名状态。支付成功后的资料刷新失败不会被前端误报为扣款失败。
- 修正购物车缩略图宽度与网格列宽不一致造成的商品名称重叠。
