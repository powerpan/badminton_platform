# 前台收银与模拟支付需求确认

确认日期：2026-09-23

状态：业务规则已确认，功能分批实现中，实际范围见 [开发记录](软件工程/开发进度与验证记录.md)。本文汇总本次对话中的客户要求与用户确认；实现注意事项用于指导后续设计，不代表功能已经交付。

## 1. 本次范围

- 提供网站访问链接，供后续放入微信公众号；本次不增加微信登录或小程序。
- 保留普通用户、管理员，增加前台人员和维修人员，共四种角色。
- 线上订场和商城消费支持储值余额、项目内模拟支付宝两种支付方式。
- 前台在自己的设备上为 walk-in 散客开场、收款，不发送到客户账户支付。
- 商城付款后生成取货核销码，由工作人员确认交付商品。
- 保留现有储值和会员等级机制，增加前台帮助客户储值的功能。
- 管理员可查询全系统订场记录和流水记录。

这里的“模拟支付宝”指项目内模拟支付接口，不调用支付宝官方沙箱或生产接口，不发生真实扣款。

## 2. 角色与职责

| 角色 | 本次明确的职责 |
| --- | --- |
| 普通用户 | 线上订场、商城消费、查看本人订单与会员账户；保留现有用户功能 |
| 前台人员 | 查看场地安排、散客开场收款、续场、取消未付款单、商品取货核销、帮助客户储值 |
| 场地管理员 | 沿用现有管理员；管理场地、用户与会员、赛事、公告、社区内容、商品、退款、维修安排；查询全部订场和流水 |
| 维修人员 | 查看需要维修的场地、维修原因和安排 |

前台不具备赛事、公告、社区内容发布权限，也不具备商品调价、会员等级调整和退款审批权限。新增的前台充值入口仅用于正金额充值，不等同于管理员现有的余额增减、积分和会员等级调整入口。维修人员第一版采用查看权限，维修登记与恢复开放由管理员操作。

## 3. 散客开场与整段计费

### 已确认规则

1. 沿用系统配置的可预约时间段，按所选完整时间段计费。
2. 例如可预约时间为 14:00–15:00，客户 14:10 到店，前台可为其开这一个仍空闲的时段，收取 14:00–15:00 的完整原价，使用截止时间仍为 15:00。
3. 不按剩余 50 分钟打折，也不把结束时间延长至 15:10。选择连续多个时段时，按各段完整原价合计。
4. 散客不使用会员折扣、不累计会员积分，也不要求绑定会员账户；姓名、联系方式可选填。
5. 订单记录实际经办前台，不把前台账号视为消费者，不扣前台账户余额。
6. 空闲判断必须同时考虑线上预约、其他前台开场、待付款占用和维修/包场安排。

### 收款与使用流程

前台选择空闲场地和时间段 → 生成散客订单并临时占场 → 前台设备完成模拟收款 → 付款成功后正式开场 → 所选时间段结束后自动结束。

- 取消未付款单或付款超时后，释放临时占用。
- 续场先检查后续完整时间段是否空闲，按原价另收费用，并关联原散客订单。
- 提前离场不自动退款。
- 到店即时开场可选当前尚未结束的空闲时间段，并可连续选择后续空闲段；不能倒填已经结束的时段。线上用户仍沿用原有未来时段预约规则。

## 4. 线上订场、商城与会员权益

| 场景 | 支付方式 | 价格与权益 |
| --- | --- | --- |
| 线上订场 | 余额 / 项目内模拟支付宝 | 沿用会员折扣和积分规则，权益不因支付方式改变 |
| 商城消费 | 余额 / 项目内模拟支付宝 | 沿用商品价格，第一版不新增商城会员折扣 |
| 散客开场及续场 | 前台设备模拟收款 | 完整时间段原价，不享会员折扣、不累计会员积分 |
| 客户储值 | 保留管理员原有操作；增加前台代充值 | 入账到指定客户的储值账户，不因充值操作自行改变会员等级或积分 |

模拟支付宝支付不扣会员余额，也不能因为会员余额不足而阻止创建该渠道的订单。待支付金额对可用余额的占用，只适用于需要占用储值余额的支付流程。

保留线上预约改期能力；差额收款、退款以及相关记录需要适配新增支付方式，不能沿用只修改余额的逻辑。

## 5. 前台帮助客户储值

新增前台充值入口，客户必须有可明确识别的会员账户；散客开场本身不要求注册。

按本次前台收银方式，采用以下实现流程：查询并确认客户 → 输入正数充值金额 → 生成充值单 → 前台设备完成模拟收款 → 收款成功后增加该客户余额。

- 确认页面展示目标客户与金额，避免充错账户。
- 每笔充值关联收款记录、目标客户、经办前台、充值时间及充值前后余额。
- 重复确认或重复支付通知只能入账一次；付款失败或取消不增加余额。
- 前台不能通过充值入口扣减余额、修改会员等级或调整积分。
- 第一版不增加用户自助充值入口，管理员原有调整能力保留并继续记录流水。

## 6. 商城取货核销与退款

商城流程：提交订单 → 待支付 → 支付成功、待取货 → 展示取货核销码 → 前台或管理员核对商品并确认核销 → 订单完成。

- 核销码用于取货确认，不是付款码；余额或模拟支付宝支付成功后均可生成。
- 核销页面显示订单、商品、数量和状态，确认交付后记录核销人及核销时间。
- 单笔订单第一版整单核销，不增加分批取货流程。
- 未支付、已退款或已核销的订单不能再次核销；退款处理中暂停核销，驳回退款后可恢复待取货状态。
- 前台可取消未付款订单；已付款退款由管理员处理，现有正常订单退款条件继续适用。
- 余额支付退回余额；模拟支付宝支付走模拟退款，不凭空增加会员余额。
- 退款、库存恢复、积分回退和核销之间需要校验订单状态，避免同一笔业务重复处理。

## 7. 管理员统一查询

### 订场记录

管理员可以查看线上预约、前台散客开场、续场，以及各自的待付款、已付款、已结束、已取消和已过期记录。记录包含：

- 订单编号、来源、场地、日期、计费时间段和金额。
- 关联会员或散客标识、实际经办人员。
- 支付方式、付款时间、退款与改期/续场关联记录。
- 实际开场或到场记录；不能将整段计费的起点冒充客户实际到场时间。

支持按日期、场地、来源、状态、支付方式、客户及经办人员筛选，并可打开详情追溯。

### 流水记录

提供全局查询入口，覆盖线上订场、散客收款、续场收款、商城消费、前台充值、管理员余额/积分调整、退款和改期差额。

每条记录展示业务类型、金额或账户变动、支付渠道、关联业务单、目标客户（如有）、经办人和时间。会员余额流水保留变动前后余额；散客交易使用其业务订单，不强行写入某个会员的余额账户。

统计应分别展示渠道收款、退款、储值充值、余额消费和人工账户调整，避免将“充值 100 元”和“随后余额消费 100 元”重复汇总为收款 200 元。模拟支付数据明确标注模拟渠道，订场统计覆盖线上与线下来源。

历史记录继续可查；缺少历史支付渠道或经办信息时明确展示历史数据状态，不编造新记录补齐。

## 8. 实现前需要处理的现有约束

- 当前角色校验只允许 `user` / `admin`；新增角色需要后端接口授权和前端入口共同生效。
- 当前订场与支付表要求关联用户，散客订单需要区分客户归属和经办人员。
- 当前线上规则拒绝已经开始的时间段；散客开场需要单独允许当前空闲时间段。付款期限也不能继续取已过去的时段开始时间，应受收款超时和所选时段结束时间约束。
- 当前商城下单即扣余额，需要引入待支付流程、库存占用和过期释放。
- 当前预约创建、商城核价和可用余额计算均依赖余额约束，需要按支付渠道分开处理。
- 当前退款、改期和部分统计依赖会员余额流水，需要补充模拟支付及散客业务记录。

## 9. 后续实施与验收顺序

1. 角色权限、数据库升级和订单/交易记录基础，保留已有数据。
2. 前台整段开场、模拟收款、续场及统一场地冲突判断。
3. 线上订场与商城模拟支付、退款、改期差额及商品核销。
4. 前台代充值、管理员全部订场和流水查询、统计口径调整。
5. 维修人员查看入口、角色界面、网站链接使用说明及回归验收。

必须覆盖的验收样例：14:10 开 14:00–15:00 的完整价格；到 15:00 不再接受该段付款；线上与前台竞争同一时段只有一方成功；续场不覆盖下一场；模拟支付不扣储值余额；两种支付方式的会员权益一致；退款不跨渠道；重复取货不重复核销；重复充值不重复入账；前台不能发布内容或改会员等级；管理员能够从订单追溯到完整流水和经办人。

本文仅固定需求与实现边界。业务功能、数据库升级和测试结果在实际实施后另行登记，不以需求文档代替验收。
