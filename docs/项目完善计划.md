## 目标与范围

面向毕业设计，将现有预约、会员、活动、商城和后台管理功能完善为可稳定演示、规则一致、界面具有球馆特色的产品。先解决真实缺陷，再改善视觉与信息结构，最后增加有明确业务价值的特色功能。

本计划依据本地代码检查、桌面 1440×1000 / 手机 390×844 页面检查，以及不连接数据库的算法样例验证。样例中发现：跨两小时预约未正确映射到一小时时段；两小时预约被按一笔计算使用率。手机预约主区域实际仅宽 42px。

### 已确定的实施边界

- 保留 Vue 3、Element Plus、Tornado、MySQL、Redis 技术栈与已有业务模块。
- 第一阶段不修改表结构，不删除用户、订单或流水，不重置数据库；用隔离测试验证边界条件。
- 不自动发布或推送。每阶段记录代码、验证证据和未覆盖范围。
- 此前明确搁置的默认管理员凭据、找回密码与旧数据取消退款安全事项，不纳入本轮实施。
- 演示数据另行提供显式脚本并使用独立数据库，不将虚构指标混入现有业务数据。
- 三个阶段已分批完成；第三批包含用户追加的输入控件多重边框修复，交易与并发验证使用独立数据库。

### 推荐算法与实验设计

- 使用统一时间槽表达预约、维护和有效临时占用；用前缀和快速判断连续窗口是否可用。
- 候选排序先满足硬性约束，按开始时间偏差、场地偏好、价格和单槽碎片稳定排序；排序规则通过样例评估，不宣称未验证的最优性。
- 实验包括不同场地/预约数量下的候选生成耗时、推荐合法性、找到场次所需操作数和剩余空档数量。
- 数据库事务仍为最终防冲突边界；Redis 与推荐结果不能替代提交校验。

### 第一阶段实现与证据

- **后端**：`utils/time_slots.py` 使用半开区间判断重叠；每次时段查询通过一次 Redis MGET 获取临时锁；应用复用 Redis 连接并在退出时关闭。`ReservationMaintenance` 每 30 秒运行，异常记录后下一轮重试，停止时等待当前清理完成。
- **业务口径**：使用率包含待支付、已确认和已完成预约的时长；总览仅统计当前启用场地，分母按当前营业规则的可预约时间计算。历史营业规则/场地启停没有快照，因此本阶段不宣称还原历史真实到场率。
- **前端**：`utils/booking.ts` 负责连续区间、费用、倒计时与截止时间格式。预约页允许所有场地，支持实际筛选；快速日期按钮加日期选择器覆盖后端规定的完整范围。异步响应带版本检查，卸载时释放刷新计时器。
- **布局**：从全局 CSS 移出 260 余行重复预约规则，集中到 `booking.css`；手机以单列主区域和底部确认栏呈现，场地和时段矩阵仅在自身容器中横向滚动。
- **真实环境**：本地 `http://localhost:5188`，Playwright + Chrome 隔离会话；当前会话没有 Browser 插件专用技能。检查 1440×1000、768×1024、390×844；页面身份、非空内容、无框架错误覆盖层、控制台和截图均核对。
- **实际交互**：登录、日期切换、相邻两时段合并、最长时长提示、手机选时、管理员统计页。已有业务余额未用于测试支付。
- **浏览器隔离响应**：第五场地、30 分钟格价、待支付占用余额、旧日期延迟响应、55 条分页及筛选回第一页、待支付倒计时到期刷新。只替换测试浏览器的接口响应，没有向数据库插入测试记录。
- **持续服务**：修改期间开发服务器自动重载遇到中间导入状态而退出；完成后已重新启动后端，验证正常退出与重启，恢复日志和进程记录，API/MySQL/Redis 健康检查通过。
