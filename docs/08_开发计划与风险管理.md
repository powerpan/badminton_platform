## 3. 总体开发原则

- 先完成核心闭环，再补充后台和统计。
- 先实现后端核心接口，再进行前端页面联调。
- 预约流程优先级最高，Redis 锁和 MySQL 冲突校验必须尽早验证。
- 管理员功能按用户、场地、预约、公告、配置、统计的顺序推进。
- 每完成一个模块，应补充对应测试用例。
- 文档、数据库结构和接口实现保持同步。

## 7. 主要风险

### 7.1 预约并发控制不完整

风险说明：

如果只在前端判断时间段状态，多个用户同时提交时仍可能产生重复预约。

应对措施：

- 后端必须使用 Redis `SET NX EX` 加锁。
- 加锁成功后仍需查询 MySQL。
- MySQL 查询需要判断时间段重叠。
- 并发测试必须覆盖同一时间段多用户同时预约。

### 7.2 Redis 锁异常导致时间段无法预约

风险说明：

如果锁没有 TTL，或异常流程没有释放锁，可能导致时间段长时间显示不可预约。

应对措施：

- Redis 锁必须设置过期时间。
- MySQL 写入失败时主动释放锁。
- 删除锁时校验锁 value。
- 管理员健康检查中显示 Redis 状态。

### 7.3 权限控制只依赖前端

风险说明：

用户可以绕过前端页面，直接请求后台接口。

应对措施：

- 后端所有管理员接口必须校验 `admin` 角色。
- 普通用户只能操作自己的数据。
- 权限测试覆盖无 token、普通用户、过期 token 等情况。

### 7.4 数据库设计过于简单

风险说明：

任务书给出的表结构较简略，如果直接照搬，后续预约状态、取消时间、操作日志等功能难以实现。

应对措施：

- 在任务书基础上补充状态、更新时间、编号、日志表等字段。
- 保留清晰索引，支持后台筛选和统计。
- 后续实现如有变化，同步更新数据库文档。

### 7.5 前后端字段不一致

风险说明：

接口字段与前端页面字段不一致，会导致联调耗时。

应对措施：

- 编码前先确认接口设计说明书。
- 前端统一通过 `api/` 模块封装请求。
- 后端返回统一 `code/message/data` 格式。

### 7.6 工期不足

风险说明：

如果一开始就做统计图表、Docker、支付等扩展功能，可能影响核心预约流程。

应对措施：

- 优先完成必须功能。
- 可选功能在核心闭环稳定后再做。
- 每周保留缺陷修复时间。

## 8. 质量控制

### 8.1 代码质量

- 后端业务逻辑不要全部写在 Handler。
- SQL 查询集中在 Repository。
- 前端请求集中在 `api/` 目录。
- 状态值使用枚举或常量管理。
- 复杂业务流程保留必要注释。

### 8.2 数据质量

- 用户名唯一。
- 场地编号唯一。
- 预约编号唯一。
- 预约状态必须在定义范围内。
- 系统配置值需要校验类型。

### 8.3 测试质量

- 核心接口至少手动测试通过。
- 预约并发场景必须测试。
- 权限场景必须测试。
- 修复缺陷后应回归相关流程。
