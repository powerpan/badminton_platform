# 系统概要设计说明书

## 1. 设计目标

BF羽毛球馆管理平台采用前后端分离架构，目标是实现普通用户预约、管理员后台维护、Redis 防重复预约、MySQL 数据持久化和基础运营统计。系统设计以简单、清晰、可实现为原则，避免过早引入复杂架构。

## 2. 总体架构

系统分为四个主要部分：

- 前端应用：提供普通用户页面和管理员后台页面。
- 后端服务：基于 Tornado 提供 REST API。
- MySQL 数据库：保存用户、场地、预约、公告、配置和日志等持久化数据。
- Redis 缓存服务：保存预约锁、短期缓存和超时释放标记。

整体调用关系如下：

```text
浏览器
  |
  | HTTP / Axios
  v
Vue3 前端应用
  |
  | REST API + JWT
  v
Tornado 后端服务
  |             |
  | SQL         | Redis 命令
  v             v
MySQL 数据库    Redis
```

## 3. 技术选型

### 3.1 前端

- Vue3：负责页面组件开发。
- Vue Router：负责用户端和管理端路由切换。
- Pinia：保存登录用户、权限、全局配置等状态。
- Axios：封装请求、响应和 JWT 请求头。

前端推荐划分为：

- 用户端页面：登录、注册、首页、场地列表、预约页面、个人中心、公告列表。
- 管理端页面：用户管理、场地管理、预约管理、公告管理、统计分析、规则配置、系统监控。
- 公共组件：导航栏、分页器、表单弹窗、状态标签、确认弹窗。

### 3.2 后端

- Tornado：提供异步 Web 服务和 API 路由。
- PyJWT：生成和解析 JWT。
- aiomysql 或同类 MySQL 客户端：访问 MySQL。
- redis-py asyncio 或同类 Redis 客户端：访问 Redis。

后端推荐划分为：

- `handlers/`：请求处理层。
- `services/`：业务逻辑层。
- `repositories/`：数据库访问层。
- `models/`：数据对象和枚举。
- `middlewares/`：认证、权限、异常处理。
- `utils/`：JWT、密码加密、响应封装、时间处理。
- `config/`：配置加载。

### 3.3 数据库

MySQL 用于保存核心业务数据。数据库设计应保证：

- 用户名唯一。
- 预约记录能关联用户和场地。
- 预约状态清晰可追踪。
- 公告支持创建和更新。
- 系统配置支持按 key 查询。
- 操作日志可追溯关键行为。

### 3.4 Redis

Redis 主要用于预约并发控制。

核心用途包括：

- 预约时段锁：防止多个用户同时预约同一场地同一时间段。
- 超时释放：通过 key 过期时间释放未确认预约。
- 热点缓存：缓存场地可用状态、系统配置等读取频繁的数据。

## 4. 模块划分

### 4.1 用户认证模块

职责：

- 用户注册。
- 用户登录。
- JWT 生成和校验。
- 角色权限判断。
- 密码加密与校验。

主要接口：

- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/auth/profile`
- `PUT /api/auth/profile`
- `PUT /api/auth/password`

### 4.2 场地预约模块

职责：

- 场地查询。
- 日期和时间段可用状态查询。
- 提交预约。
- 取消预约。
- 预约冲突判断。
- Redis 锁管理。

主要接口：

- `GET /api/courts`
- `GET /api/courts/{id}/slots`
- `POST /api/reservations`
- `GET /api/reservations/my`
- `PUT /api/reservations/{id}/cancel`

### 4.3 公告模块

职责：

- 用户查看公告列表和详情。
- 管理员发布、编辑和删除公告。

主要接口：

- `GET /api/announcements`
- `GET /api/announcements/{id}`
- `POST /api/admin/announcements`
- `PUT /api/admin/announcements/{id}`
- `DELETE /api/admin/announcements/{id}`

### 4.4 管理后台模块

职责：

- 用户管理。
- 场地管理。
- 预约记录维护。
- 统计分析。
- 系统规则配置。
- 操作日志查询。
- 系统健康检查。

主要接口前缀：

- `/api/admin/users`
- `/api/admin/courts`
- `/api/admin/reservations`
- `/api/admin/statistics`
- `/api/admin/configs`
- `/api/admin/logs`
- `/api/admin/health`

## 5. 权限设计

系统角色分为：

- `user`：普通用户。
- `admin`：系统管理员。

权限控制原则：

- 未登录用户只能访问注册、登录和公开公告接口。
- 普通用户只能访问自己的个人信息和预约记录。
- 管理员可以访问后台管理接口。
- 所有 `/api/admin/**` 接口都必须校验管理员角色。

JWT 中建议包含：

- `user_id`
- `username`
- `role`
- `exp`

## 6. 数据流设计

### 6.1 登录数据流

```text
用户输入账号密码
  -> 前端提交登录请求
  -> 后端校验用户名和密码
  -> 后端生成 JWT
  -> 前端保存 JWT 和用户信息
  -> 后续请求携带 Authorization 请求头
```

### 6.2 预约数据流

```text
用户选择日期、时间段和场地
  -> 前端提交预约请求
  -> 后端校验登录态和参数
  -> 后端检查用户和场地状态
  -> 后端使用 Redis 尝试加锁
  -> 后端检查 MySQL 是否已有有效预约
  -> 后端写入预约记录
  -> 后端返回预约结果
```

### 6.3 管理员维护数据流

```text
管理员登录后台
  -> 前端携带 JWT 请求后台接口
  -> 后端校验 admin 角色
  -> 后端执行用户、场地、预约、公告等维护操作
  -> 后端写入操作日志
  -> 前端刷新列表或详情
```

## 7. 异常处理设计

后端统一返回 JSON，不直接向前端暴露堆栈信息。

推荐返回格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

常见错误码：

| code | 含义 |
| --- | --- |
| 0 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录或登录过期 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 业务冲突，例如重复预约 |
| 500 | 系统内部错误 |

## 8. 部署视图

本地开发环境建议部署为：

```text
Vue3 Dev Server   http://localhost:5188
Tornado API       http://localhost:8000
MySQL             localhost:3306
Redis             localhost:6379
```

生产环境可使用 Nginx 托管前端静态文件，并将 `/api` 请求转发到 Tornado 服务。

```text
Nginx
  |-- 静态文件：Vue3 build 产物
  |-- /api 反向代理：Tornado 服务
Tornado
  |-- MySQL
  |-- Redis
```

## 9. 关键设计约束

- 预约冲突判断必须同时依赖 Redis 锁和 MySQL 最终校验。
- Redis 锁只能解决并发窗口问题，不能代替数据库中的预约记录。
- 预约写入必须使用 MySQL 短事务兜底，事务内重新校验时间重叠、每日次数、用户状态和场地状态。
- 管理员禁用用户、停用场地前必须检查未来有效预约，避免破坏已有预约。
- 前端敏感操作需要二次确认，但真正的限制仍以后端校验为准。
- 管理员后台接口必须独立做权限校验。
- 前端不能信任本地角色信息，后端必须重新校验 JWT。
- 系统配置变更后应及时影响后续预约判断。
