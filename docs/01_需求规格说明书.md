# 需求规格说明书

## 1. 项目概述

BF羽毛球馆管理平台面向羽毛球馆的日常预约和后台管理场景，解决传统人工管理中常见的预约冲突、场地状态不透明、运营数据难统计等问题。系统采用 Web 方式提供服务，普通用户可以在线查看场地并提交预约，管理员可以维护用户、场地、预约、公告和系统规则。

## 2. 用户角色

### 2.1 普通用户

普通用户是平台的主要使用者，主要目标是快速了解场地可用情况，并完成预约、查看和取消操作。

普通用户需要完成的操作包括：

- 注册账号。
- 登录系统。
- 查看羽毛球场地列表和场地状态。
- 按日期和时间段查询可预约场地。
- 提交场地预约。
- 查看个人预约记录。
- 在规则允许范围内取消预约。
- 修改个人昵称、联系方式和密码。
- 浏览平台公告。

### 2.2 系统管理员

系统管理员负责平台基础数据维护和运营管理。

管理员需要完成的操作包括：

- 登录后台管理系统。
- 查看、新增、禁用普通用户。
- 分配用户角色。
- 新增、编辑、启用和停用场地。
- 查看、审核和维护预约记录。
- 发布、编辑和删除平台公告。
- 查看预约热度、用户活跃度、场地使用率等统计数据。
- 配置最大预约时长、预约超时时间等系统规则。
- 查看系统操作日志和服务健康状态。

## 3. 功能需求

### 3.1 注册与登录

- 用户可以使用用户名、密码和联系方式注册账号。
- 用户名不能重复。
- 密码应加密保存，不能以明文形式存入数据库。
- 登录成功后，后端返回 JWT。
- 前端后续请求需要在请求头中携带 JWT。
- 系统根据 JWT 中的用户身份和角色控制访问权限。

### 3.2 个人信息管理

- 用户可以查看自己的账号信息。
- 用户可以修改昵称和联系方式。
- 用户可以修改密码。
- 修改密码时需要校验旧密码。
- 用户不能直接修改自己的角色和账号状态。

### 3.3 场地浏览

- 用户可以查看所有启用状态的羽毛球场地。
- 场地信息包括场地编号、场地名称、状态、创建时间等。
- 用户可以按日期查看场地在不同时间段的可预约情况。
- 已预约、已锁定、停用的场地时间段不能再次预约。

### 3.4 在线预约

- 用户选择日期、时间段和场地后提交预约。
- 系统需要先通过 Redis 对目标场地和时间段加锁。
- 同一场地、同一日期、同一时间段只能存在一个有效预约。
- 加锁成功后写入预约记录。
- 如果预约流程未在规定时间内确认完成，锁需要自动释放。
- 预约成功后，预约状态为已确认或待确认，具体状态由后续实现规则决定。

### 3.5 预约记录查看与取消

- 用户可以查看自己的全部预约记录。
- 用户可以按状态筛选预约记录。
- 用户可以取消尚未开始且规则允许取消的预约。
- 取消后需要释放对应时间段的占用状态。
- 已完成、已过期或被管理员锁定的预约不能由用户取消。

### 3.6 公告浏览

- 用户可以查看管理员发布的平台公告。
- 公告列表按发布时间倒序展示。
- 用户可以查看公告详情。

### 3.7 用户管理

- 管理员可以查看用户列表。
- 管理员可以按用户名、联系方式、角色、状态筛选用户。
- 管理员可以新增用户。
- 管理员可以禁用或启用用户。
- 管理员可以为用户分配普通用户或管理员角色。
- 被禁用用户不能登录系统。

### 3.8 场地管理

- 管理员可以新增场地。
- 管理员可以编辑场地名称和状态。
- 管理员可以启用或停用场地。
- 停用场地不能被普通用户预约。
- 对已有有效预约的场地，停用时需要给出明确提示，避免影响已预约用户。

### 3.9 预约记录管理

- 管理员可以查看全部预约记录。
- 管理员可以按用户、场地、日期、状态筛选预约。
- 管理员可以维护异常预约记录。
- 管理员可以取消违规预约。
- 管理员操作应写入系统操作日志。

### 3.10 公告管理

- 管理员可以发布公告。
- 管理员可以编辑公告标题和内容。
- 管理员可以删除公告。
- 公告需要记录创建时间和更新时间。

### 3.11 数据统计

系统需要提供基础运营统计，至少包括：

- 预约总数。
- 每日预约数量。
- 场地使用率。
- 热门预约时间段。
- 活跃用户数量。

统计数据主要用于后台展示，不要求复杂的数据仓库设计。

### 3.12 系统规则配置

管理员可以配置系统规则，至少包括：

- 单次最大预约时长。
- 预约超时释放时间。
- 可提前预约天数。
- 用户每日最大预约次数。

规则配置应保存在数据库中，后端读取后参与业务判断。

### 3.13 日志管理与健康监控

- 系统需要记录关键操作日志。
- 管理员可以查看用户操作和管理员操作。
- 系统需要提供健康检查接口，展示后端服务、MySQL 和 Redis 的连接状态。

## 4. 非功能需求

### 4.1 性能需求

- 常规列表查询应在 1 秒内返回。
- 预约操作应尽量控制在 2 秒内完成。
- Redis 锁需要保证高并发场景下同一时间段不会被重复预约。

### 4.2 安全需求

- 密码必须加密存储。
- 登录态使用 JWT 管理。
- 管理员接口必须校验管理员角色。
- 普通用户只能访问自己的预约和个人信息。
- 请求参数需要进行基础校验，避免非法数据写入。

### 4.3 可维护性需求

- 后端接口按模块拆分。
- 前端页面按用户端和管理端拆分。
- 配置项通过配置文件或环境变量管理。
- 数据库表字段和接口字段命名保持清晰一致。

### 4.4 可用性需求

- 普通用户操作流程应简单，预约入口清晰。
- 管理员后台应支持基础筛选和分页。
- 错误提示应明确说明失败原因。
- 系统异常时不应泄露后端堆栈信息给前端用户。

## 5. 业务约束

- 同一场地、同一日期、同一时间段不能重复预约。
- 停用场地不能新增预约。
- 被禁用用户不能登录和预约。
- 未登录用户只能访问登录、注册和公开公告等允许匿名访问的接口。
- 管理员权限不能由普通用户自行修改。

## 6. 验收标准

项目完成时应满足以下验收条件：

- 普通用户可以完成注册、登录、查看场地、提交预约、查看预约、取消预约和查看公告。
- 管理员可以完成用户、场地、预约、公告、规则和统计管理。
- Redis 预约锁能阻止重复预约。
- 预约超时释放逻辑可以正常执行。
- MySQL 中的核心业务数据保存完整。
- 前后端通过 API 正常通信。
- 系统提供基本测试用例和部署说明。
