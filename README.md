# BF 羽毛球馆管理平台

面向羽毛球馆日常运营的前后端分离 Web 应用，将**线上预约、到店开场、会员储值、消费结算、商品取货和经营管理**整合到同一套系统中，为普通用户、前台、管理员和维修人员提供各自的工作区。

项目使用 **Vue 3 + TypeScript + Tornado + MySQL + Redis**，以异步 I/O、数据库事务与行锁、请求幂等和资源占用管理应对并发预约与收款。支持电脑、平板和手机访问，可用于毕业设计展示与全栈开发学习。

核心特点：**四角色协作 · 连续场次推荐 · 并发冲突控制 · 双渠道结算 · 一次性取货核销 · 全局流水追溯**。并发实现与本地性能数据见下方[高并发场景设计与验证](#高并发场景设计与验证)。

## 主要功能

### 用户端

| 模块 | 功能 |
| --- | --- |
| 场地预约 | 查看场地时间表与维护占用、连续选时、会员报价、储值余额或模拟支付宝付款、付款倒计时、取消退款与改期差额结算 |
| 场次推荐 | 根据日期、最早开始时间、运动时长和场地偏好，推荐连续可用的场次并说明推荐原因 |
| 会员中心 | 个人资料、会员权益、余额与积分、柜台储值及账户流水查询 |
| 赛事活动 | 浏览活动、查看详情、报名和取消报名，展示报名人数与截止时间 |
| 器材商城 | 浏览商品、购物车、实时核价、余额/模拟支付宝付款、取货二维码与可读码、订单查询和退款申请 |
| 球友交流 | 发布与浏览交流动态、隐藏自己的动态，浏览球馆公告和站内通知 |

### 管理端

| 模块 | 功能 |
| --- | --- |
| 场地与预约 | 维护场地、维护/包场时段；按来源、渠道、客户、经办和单号查询全部订场，追溯续场链、收退款及改期 |
| 用户与会员 | 四角色分配、账号状态、会员等级与权益、余额/积分人工调整；模拟收款储值、全部充值记录及到账凭证 |
| 内容与活动 | 管理公告、通知、赛事活动及球友圈内容 |
| 商城管理 | 商品上下架、实物/预留/可售库存、整单取货核销与原渠道退款审核 |
| 全局流水 | 统一查询支付、退款、储值和账户变动，按来源、渠道、客户、经办人和单号筛选，查看分类汇总与账户核对 |
| 经营统计 | 按日期查看预约趋势、时段热度、预订率、取消率、退款和到场记录 |
| 规则与日志 | 配置营业时间、预约期限、最长时长等规则，查询操作日志与服务状态 |

### 场馆工作人员

| 角色 | 工作内容 |
| --- | --- |
| 前台 | 查看当日场地安排，为散客整段开场、在柜台设备模拟收款、办理相邻续场、会员代储值与商品取货核销 |
| 维修人员 | 查看明确归类的维修场地、原因、日期和状态，场地恢复由管理员处理 |

散客无需先注册，按完整时间段原价收费：例如 14:10 到店选择 14:00–15:00，仍按该完整时段收费，并在 15:00 结束。线上订场保留会员折扣和积分规则；前台不能发布赛事、公告等运营内容，维修人员只读查看安排。

当前支付宝流程均为**项目内模拟**，不发生真实转账，尚未接入支付宝官方沙箱或正式支付。商城付款成功后生成的是取货凭证，需由前台或管理员查询并确认交付。

## 设计特点

- **线上与柜台共用场地安排**：线上预约、散客开场、续场、改期、维护及包场使用统一冲突规则，避免不同入口各自登记造成重复占场；记录客户、经办人和关联订单，管理员可追溯完整业务过程。
- **可解释的连续场次推荐**：使用前缀和筛选完整空闲窗口，依次按开始时间偏差、场地偏好、价格和零散空档排序，返回最多三个候选场次及推荐理由。扫描复杂度为 O(CS)，候选排序为 O(K log K)，其中 C 为场地数、S 为每场地时段数、K 为候选数；推荐不占位，最终下单再次校验。见[算法实现](backend/utils/booking_operations.py)。
- **统一支付与会员结算**：订场与商城支持储值余额和模拟支付宝，金额使用整数分计算；退款退回原渠道，改期按差额补付或退还。模拟支付宝退款不会增加会员储值余额，预约会员优惠与积分按规则计算。
- **结算前重新核价**：商城确认时重新获取价格、库存和可用余额；预约及改期核对用户确认的报价，发现变动后要求重新确认。已创建的有效待付订单保留成交价格快照。
- **付款、库存和交付联动**：商城待付订单预留库存，付款成功生成取货二维码和可读码；查询凭证后再确认整单交付，同一订单只能核销一次。退款申请期间冻结取货，退款成功后凭证失效。
- **可核对的经营数据**：区分渠道收款、储值充值、余额消费和退款，例如“充值 100 元后余额消费 100 元”不会被重复统计为 200 元渠道收款；预约结束、到场核销和未到场分别记录，到场率同时披露记录覆盖情况。
- **贴近场馆操作的界面**：采用场地编号与场馆导视风格。桌面端以时间表和费用清单组织操作，手机端使用单场地选时与费用抽屉；后台按业务模块拆分，支持筛选、分页和抽屉编辑。

## 高并发场景设计与验证

系统针对多人同时订场、抢购剩余库存、重复付款和并发储值等场景，结合异步处理与数据库约束控制资源竞争。

| 机制 | 当前实现与作用 |
| --- | --- |
| 异步请求与连接复用 | Tornado 配合 `async/await`、aiomysql 连接池和 `redis.asyncio` 处理 I/O；bcrypt 密码计算放在线程中执行，减少阻塞事件循环。默认每进程 MySQL 连接池上限为 10 |
| 统一场地冲突控制 | 线上预约、到店开场、续场、改期与维护在事务中锁定相关场地行，再检查时间区间和有效占用，避免多个入口同时占用同一场次 |
| 库存与余额保护 | 商品行、会员账户行及相关业务记录加锁；待付订单预留库存或余额，付款、取消和过期时按状态处理，防止超卖和重复扣款 |
| 请求幂等与唯一约束 | 保存请求号、参数摘要和处理结果，重复提交可返回原结果，同号变参拒绝；支付业务键、充值请求、账户入账效果和取货凭证有数据库唯一约束 |
| Redis 临时状态 | 复用异步客户端，批量读取临时锁，使用带 TTL 的临时状态及校验持有者的 Lua 解锁；承载验证码、登录失败计数、刷新令牌和既有临时锁。当前新预约的占场与防重以 MySQL 事务为准 |
| 超时与失败恢复 | 定时任务清理过期订单，请求入口也校验截止时间；关键交易中的业务状态、账户/库存变化、流水与审计同事务提交，异常整体回滚，断连后可查询原单恢复结果 |

实现入口：[数据库连接池](backend/repositories/database.py)、[事务边界](backend/repositories/transaction.py)、[线上预约事务](backend/repositories/customer_booking_repository.py)、[支付共用逻辑](backend/repositories/payment_common.py)、[Redis 服务](backend/services/redis_service.py)。

### 已记录的本地并发测试

2026-09-24 在 macOS arm64、Python 3.14.3、MySQL 5.7.28、数据库连接池上限 10 的隔离环境中，通过真实 Tornado HTTP 路由、JWT 与角色校验进行测量。每类先执行 1 次首请求，再以 **20 并发上限执行 200 次请求**：

| 场景 | P50 | P95（95% 请求不超过） | 失败次数 |
| --- | --- | --- | --- |
| 商城结算报价 | 15.39 ms | 17.93 ms | 0 / 200 |
| 商城模拟收款 | 61.00 ms | 74.46 ms | 0 / 200 |
| 管理员全局流水列表 | 305.47 ms | 349.48 ms | 0 / 200 |

该轮使用 20 个客户、1 种商品及 201 笔不同的待付订单，收款后核对支付单、取货凭证、库存、销量和账户变动，结果一致。独立集成检查还覆盖了并发占场、最后一件库存竞争、同一支付单重复确认、充值只入账一次，以及退款与取货互斥。详见[性能原始结果](docs/软件工程/验证结果/2026-09-24-性能.json)与[验收用例追踪](docs/软件工程/D06用例追踪.md)。

以上是**并发控制设计及本地 20 并发样本的验证结果**，不代表千级并发或生产环境 QPS 上限；测量未覆盖公网、多实例部署或大规模历史数据。同一热门场地的写入需要等待行锁，更高负载下的吞吐量仍需在目标部署环境压测。

复现性能测量可在完成环境配置后，于仓库根目录执行：

```bash
backend/.venv/bin/python -B scripts/benchmark_staff_payments.py
```

脚本需要 MySQL 建库权限，只创建和清理自己的临时数据库，不对业务库执行测试交易。

## 技术栈

| 层次 | 技术 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、Vue Router、Pinia、Axios、响应式 CSS |
| 后端 | Python、Tornado、异步请求处理、分层业务服务 |
| 数据存储与并发控制 | MySQL / InnoDB、aiomysql 异步连接池、事务、行锁、唯一约束 |
| 临时状态与锁 | Redis、redis.asyncio、TTL、Lua 安全解锁 |
| 身份认证 | JWT、bcrypt 密码哈希、用户/前台/管理员/维修四角色权限校验 |
| 测试与构建 | Python unittest、Node.js Test Runner、vue-tsc、Vite |

前端通过 HTTP API 与后端通信；后端按 `handlers → services → repositories` 分层，分别处理请求、业务规则和数据库访问。

## 运行与演示

首次运行请按 [部署说明](docs/部署说明.md) 准备 Python、Node.js、MySQL 和 Redis，完成环境配置与数据库初始化。配置完成后，可在 macOS 终端执行：

```bash
./start-dev.command
```

默认前端地址为 `http://localhost:5188`，后端健康检查地址为 `http://localhost:8000/api/health`。旧版本数据库的升级步骤、手动启动方式和生产部署参考也在部署说明中。

仓库提供两种演示数据工具：通过 [独立演示环境](docs/演示环境.md) 创建完整的新演示库，或按 [内容填充与配图](docs/内容填充与配图.md) 为本地开发库补充活动、公告和交流话题。示例内容标注为演示，生成图片标注为场景示意；Git 仓库包含脚本与图片，数据库记录需要在目标环境另行导入。
